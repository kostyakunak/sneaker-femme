# Структура репозиториев и что выгружать в Git

## 📋 Рекомендация: Один репозиторий

Для EverShop рекомендуется использовать **один репозиторий**, так как это монолитное SSR приложение.

## ✅ Что ВЫГРУЖАТЬ в Git

### Обязательно:
- ✅ Весь исходный код (`packages/`, `extensions/`)
- ✅ Конфигурационные файлы (`config/`, `package.json`, `tsconfig.json`)
- ✅ Переводы (`translations/`)
- ✅ Docker файлы (`Dockerfile`, `docker-compose.yml`)
- ✅ Railway конфигурация (`railway.json`)
- ✅ Документация (`.md` файлы)
- ✅ `.gitignore`, `.dockerignore`

### Условно:
- ⚠️ **`public/`** - Выгружать только если содержит статические файлы, которые не генерируются. Если генерируется при сборке - не выгружать.
- ⚠️ **`seed/`** - Выгружать если нужны тестовые данные для разработки. Для production обычно не нужны.

## ❌ Что НЕ выгружать в Git

### Никогда не выгружайте:
- ❌ **`node_modules/`** - Устанавливается через `npm install`
- ❌ **`.evershop/`** - Генерируется при сборке
- ❌ **`dist/`** - Генерируется при сборке
- ❌ **`.env`** - Содержит секреты и переменные окружения
- ❌ **`media/`** - Медиа файлы (изображения, загруженные пользователями)
  - Для production используйте S3 или Azure Storage
  - Для разработки можно хранить локально, но не в Git
- ❌ **Логи** (`*.log`)
- ❌ **Временные файлы** (`.DS_Store`, `Thumbs.db`)

## 🔒 Секреты и переменные окружения

### НЕ выгружайте:
- ❌ `.env` файл
- ❌ Любые файлы с паролями, API ключами, токенами

### Вместо этого:
- ✅ Используйте переменные окружения в Railway
- ✅ Создайте `.env.example` (без реальных значений) для документации
- ✅ Используйте Railway Variables для production

## 📦 Медиа файлы

### Проблема:
Медиа файлы (изображения продуктов, загруженные пользователями) не должны быть в Git, так как:
- Они занимают много места
- Они часто меняются
- Git не предназначен для бинарных файлов

### Решение:
1. **Для production**: Используйте расширения:
   - `s3_file_storage` (AWS S3)
   - `azure_file_storage` (Azure Blob Storage)

2. **Для разработки**: Храните локально, но добавьте `media/` в `.gitignore`

3. **Для миграции**: Если нужно перенести существующие медиа файлы:
   - Загрузите их в S3/Azure
   - Или используйте отдельный сервис хранения файлов

## 🚀 Процесс первого коммита

### 1. Проверьте .gitignore

Убедитесь, что `.gitignore` содержит:
```
node_modules/
.evershop/
dist/
.env
*.log
media/
.DS_Store
```

### 2. Инициализация Git

```bash
cd evershop-dev
git init
git add .
git status  # Проверьте, что нет лишних файлов
```

### 3. Первый коммит

```bash
git commit -m "Initial commit: EverShop setup for Railway"
```

### 4. Создание репозитория на GitHub

1. Создайте новый репозиторий на GitHub
2. НЕ добавляйте README, .gitignore, license (они уже есть)
3. Скопируйте URL репозитория

### 5. Подключение remote

```bash
git remote add origin https://github.com/yourusername/your-repo.git
git branch -M main
git push -u origin main
```

## 🔄 Обновление репозитория

### После изменений:

```bash
# Проверьте статус
git status

# Добавьте изменения
git add .

# Проверьте, что добавляете правильные файлы
git status

# Закоммитьте
git commit -m "Описание изменений"

# Запушьте
git push
```

### Railway автоматически:
- Обнаружит изменения
- Пересоберет приложение
- Перезапустит сервис

## ⚠️ Важные замечания

### 1. Размер репозитория
- Если репозиторий становится слишком большим (>100MB), проверьте:
  - Нет ли `node_modules/` в Git
  - Нет ли `media/` файлов
  - Нет ли больших бинарных файлов

### 2. История коммитов
- Не коммитьте секреты даже в старые коммиты
- Если случайно закоммитили секрет:
  1. Немедленно измените секрет (API ключ, пароль)
  2. Используйте `git filter-branch` или `git filter-repo` для удаления из истории

### 3. Ветки
- `main` - для production
- `develop` - для разработки (опционально)
- Feature branches - для новых функций

## 📊 Альтернативный вариант: Разделение репозиториев

Если вы все же хотите разделить (не рекомендуется для SSR):

### Backend репозиторий:
- Весь код приложения
- API endpoints
- База данных миграции

### Frontend репозиторий:
- Потребуется создать новый фронтенд
- Статические файлы для Netlify
- API клиент для связи с backend

⚠️ **Это потребует значительной переработки архитектуры!**
